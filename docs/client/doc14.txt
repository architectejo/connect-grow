1. Objet
Ce document est la porte d'entrée officielle de la documentation de la Plateforme Écosystème RDC. Il indique ce que contient chaque
document, lequel fait autorité pour chaque type de décision, comment les documents se complètent, dans quel ordre les équipes doivent
les lire et comment gérer les évolutions sans créer de contradictions.

Il ne remplace aucun référentiel spécialisé. Il orchestre la suite documentaire.

11. Registre des décisions verrouillées - principes structurants
        Un seul compte peut supporter plusieurs activités/contextes; buyer/seller/candidate/etc. ne sont pas des types de compte.
        Navigation permanente: Accueil · Explorer · + Publier · Messages · Compte.
        + Publier est la porte universelle de création, filtrée par contexte, permissions et entitlements.
        Architecture V1: modular monolith avec frontières métier strictes et coordination event-driven.
        Permissions/roles sont séparés des entitlements commerciaux.
        Verification ne peut jamais être achetée et n'est pas une garantie de sécurité/qualité.
        Pas de universal trust score.
        Pas de pourcentage de plateforme sur ventes, prestations ou salaires comme modèle principal.
        Marketplace V1 inclut Order + Mobile Money lorsque provider approuvé + cash + pickup/delivery basique.
        Food Order et Delivery Request ont des cycles de vie séparés.
        Livraison via sociétés partenaires; pas de flotte propriétaire V1.
        Event Commerce et ticketing payant font partie de V1.
        Recruitment V1 est substantiel mais sans verdict d'embauche autonome.
        Workforce Training & Development fait partie de V1.
        Pas de profil public d'enfant.
        Pas de wallet/stored balance, lending ou general escrow V1.
        Les règles marché/légales/taxonomiques/prix doivent être configurables, pas hard-coded.
        Les états Order, Payment, Fulfillment, Delivery, Refund et Case restent indépendants.
        Tout changement monétaire doit être traçable à une source autoritative ou une action admin auditée.

18. Cahier des charges développeur - rôle
Le cahier des charges complet sert de document de handoff narratif et architectural. En cas de détail spécialisé ou de divergence apparue
après sa rédaction, les Documents 01-14 les plus récents et explicitement verrouillés prévalent pour leur domaine. Toute évolution
importante doit ensuite être répercutée dans une nouvelle version du cahier des charges ou un addendum.




19. Gouvernance des versions
    Règle                                                                    Application
    Version visible                                                          Chaque document porte version/date.
    Changelog                                                                Toute modification structurante indique ce qui a changé.
    Stable IDs                                                               Feature IDs, permission codes, taxonomy IDs, legal IDs, test IDs ne sont pas recyclés.
    Superseded                                                               Ancienne décision conservée mais marquée remplacée.
    Cross-reference                                                          Une modification affectant d'autres docs crée une liste d'impact.
    Approval                                                                 Owner métier/tech/legal selon domaine.
    Release baseline                                                         Avant build majeur, figer une baseline documentaire.
    Archive                                                                  Conserver anciennes versions pour audit/historique.

28. Ce qui ne doit jamais devenir une source de vérité
       Un mockup généré visuellement.
       Un prix illustratif utilisé dans une présentation.
       Une phrase marketing.
       Un statut affiché uniquement côté frontend.
       Une hypothèse financière du Document 04 présentée comme résultat garanti.
       Une décision juridique non validée.
       Un rôle commercial ou plan utilisé comme permission.
       Un message de support utilisé pour modifier silencieusement un état financier.
       Une catégorie hard-codée dans une app cliente.
       Un tableur local non versionné qui contredit les référentiels maîtres.

35. Règle finale
La documentation forme un système, pas une pile de fichiers indépendants. Une décision structurante doit pouvoir être suivie depuis le
besoin fonctionnel jusqu'au parcours, aux objets de données, à l'autorisation, aux règles commerciales ou de confiance, aux tests, aux
opérations et au lancement. Lorsqu'une décision change, son impact documentaire doit être explicite avant que le code devienne la
nouvelle vérité par accident.
